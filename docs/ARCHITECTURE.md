# 实现说明

## 组成

- `music_calendar/store.py`：SQLite schema、候选合并、初听校验、原始响应归档、冲突、按月查询。
- `music_calendar/client.py`：串行 JSON-lines 通道，管着 Node 子进程和超时。
- `music_calendar/provider.cjs`：账号凭据只在内存里用；读 macOS 官方客户端 Cookie 或 `NETEASE_COOKIE`。只开放项目需要的只读模块。
- `music_calendar/sync.py`：发现候选、逐首查询、请求间隔、暂停和失败恢复。
- `music_calendar/server.py`：本机 HTTP，负责连接账号、采集控制、状态、月历、搜索和导出。
- `web/`：原生 HTML、CSS、JavaScript，同源 API，没有外部字体或分析服务。

## 去重与冲突

候选主键 `(uid, song_id)`，来源单独留。初听事实同样按账号和歌曲唯一；观测按 `(uid, song_id, first_listen_ms)` 唯一。重复导入不加新事实；不同初听时间都留下来，显示最早采到的那一个。

时间存成 Unix 毫秒；按北京时间月份边界查，免得 UTC 把日子搞错。秒级时间、未来时间或不匹配的歌曲 ID 直接拒绝。

## 暂停与接着来

每首歌查完就落盘。暂停会等当前请求回来；剩下的还在排队。再开时把上次没结束的标成中断，已有结果跳过。失败的下一批再试，空结果满 30 天自动补，也可以提前补。登录失效、权限、风控或限流立刻停；连续三首出错也停。

命令行对数据目录加进程文件锁，网页和 CLI 不会抢着采。一个任务里每首只问一次。

## 本机访问

服务绑在 `127.0.0.1`，检查 Host 和写请求的 Origin，不回跨域许可。改状态要 JSON。Cookie 不进 Python、HTTP 响应或原始档案；Node 也不序列化可能带请求头的上游异常。数据库和原始响应只给本机用户读写。

以后要远程访问的话，再加身份验证、HTTPS 和按用户隔离——别直接把现在这个服务挂到公网。

## 两边差在哪儿

本机版从近期、累计与本周排行、喜欢和自建歌单找歌；Cloudflare 版还能翻历年月榜和年度报告，并记下检查点。两边都会有「回忆坐标」空着的歌，状态留着下次再问。上游规则和网络状况不归本项目管；核心测试不依赖上游。

Cloudflare 的浏览器存储、会话、同步器和部署见 [部署说明](CLOUDFLARE.md)。
